Let me give you the crisp, technically correct breakdown.

---

## 🧩 SQL itself is **not** a programming language  
SQL is a **declarative DSL** (domain‑specific language).  
It cannot express:

- loops  
- branching  
- conditionals  
- variables  
- general algorithms  
- data structures  
- control flow  

So SQL alone is **not** a programming language — full stop.

---

## 🧩 But… PL/SQL, T‑SQL, ESQL, and similar extensions *are* programming languages  
These are **procedural extensions** built *around* SQL.

They add:

- **variables**
- **loops** (`FOR`, `WHILE`)
- **conditionals** (`IF`, `CASE`)
- **functions & procedures**
- **exception handling**
- **control flow**
- **packages/modules**
- **stateful logic**

That’s what transforms SQL into something capable of general computation.

### Examples:

### **PL/SQL** (Oracle)
```sql
DECLARE
  total NUMBER := 0;
BEGIN
  FOR r IN (SELECT amount FROM orders) LOOP
    total := total + r.amount;
  END LOOP;
  DBMS_OUTPUT.PUT_LINE(total);
END;
```

### **T‑SQL** (SQL Server)
```sql
DECLARE @total INT = 0;

SELECT @total = @total + amount
FROM orders;

PRINT @total;
```

### **Embedded SQL (ESQL)**  
SQL embedded inside C, Java, COBOL, etc., where the host language provides the programming capabilities.

---

## 🧩 The key distinction  
Here’s the academically precise statement:

> **SQL is a declarative language.  
> PL/SQL, T‑SQL, and ESQL are procedural languages that embed SQL and *are* programming languages.**

This is the same classification used in:

- ANSI/ISO SQL standards  
- Oracle documentation  
- SQL Server documentation  
- Database theory textbooks  

---

## 🧠 Why this matters  
Understanding this distinction helps you reason about:

- **query optimization** (SQL is declarative → optimizer decides the plan)  
- **stored procedures** (procedural → you control the flow)  
- **performance tuning** (procedural logic can be slower inside the DB)  
- **architecture decisions** (business logic in DB vs in application code)
