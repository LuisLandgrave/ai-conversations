Java String Constants: Maintainability Over Deduplication

OK, but let's go ones step back... I'm referring to how to declare them.
I'm already aware about all those special considerations when there's a need to handle them programatically, 
but in real-world scenarios, most of the times SonarQube MAKES you create them as constants and just shoving 
them all in a static utility class may not be the best way to do it

Ahhh, that’s actually the more interesting problem 😄.

Most “String best practices” discussions focus on manipulation. In large Java codebases, the real pain is often:

How do we organize string literals without ending up with a 5,000-line Constants.java file that Sonar forced us into?

And frankly, I think some teams misunderstand Sonar’s intent.

First: Not Every String Should Become a Constant

A common anti-pattern:

public static final String ERROR = "ERROR";
public static final String ACTIVE = "ACTIVE";
public static final String YES = "YES";
public static final String NO = "NO";

just because Sonar detected duplication.

  • Technically compliant.
  • Practically terrible.

When I read:

if (Constants.ACTIVE.equals(status))

I’ve learned nothing.

When I read:

if ("ACTIVE".equals(status))

the meaning is immediately obvious.

My Rule

If the literal itself is the business meaning:

"ACTIVE"
"INACTIVE"
"PENDING"

➡️ Consider an enum instead.

public enum Status {
    ACTIVE,
    INACTIVE,
    PENDING
}

Then:

if (status == Status.ACTIVE)

which is dramatically better.

Where Constants Actually Make Sense

I usually ask:

“Would changing this value require changing multiple places?”

If yes → constant.

Good Candidate #1: Regex

private static final String EMAIL_REGEX = "...";

or

private static final Pattern EMAIL_PATTERN = Pattern.compile(...);

Makes sense.

Regexes are difficult to understand and likely reused.

Good Candidate #2: JSON Keys

public static final String CUSTOMER_ID = "customerId";
public static final String ORDER_ID = "orderId";

because:

jsonNode.get(CUSTOMER_ID);

prevents typo bugs.

Good Candidate #3: Database Columns

public static final String COL_ID = "id";
public static final String COL_NAME = "name";

especially when using JDBC.

Good Candidate #4: External Contract Values

public static final String HEADER_CORRELATION_ID = "X-Correlation-Id";

These strings represent a contract.

That’s important.

Where Utility Classes Become Horrible

Many projects eventually get:

public final class Constants {
 
public static final String YES = "YES";
public static final String NO = "NO";
 
public static final String ACTIVE = "ACTIVE";
 
public static final String CUSTOMER_ID = "customerId";
 
public static final String ERROR_MSG = "Error";
 
...
}

5000 lines later:

Constants.CUSTOMER_ID
Constants.ERROR_17
Constants.FILE_SEPARATOR
Constants.SERVICE_URL

Nobody knows where anything belongs.

Better Approach: Context-Based Constants

Instead of:

Constants

do:

CustomerConstants
OrderConstants
JsonFields
ApiHeaders
DatabaseColumns
RegexPatterns

Example:

public final class ApiHeaders {
     
    private ApiHeaders() {}
     
    public static final String CORRELATION_ID = "X-Correlation-Id";
     
    public static final String REQUEST_ID = "X-Request-Id";

}

Now usage is self-documenting:

ApiHeaders.CORRELATION_ID

Even Better: Put Constants Near Their Usage

This is the approach many senior teams use.

Instead of:

shared/constants/Constants.java

put:

customer/
├─ CustomerService
├─ CustomerRepository
└─ CustomerConstants

Only customer code sees customer constants.

This reduces coupling tremendously.

My Favorite Pattern: Nested Constant Groups

For larger domains:

public final class CustomerContract {
 
    private CustomerContract() {}
     
    public static final class Json {
        public static final String ID = "id";
        public static final String NAME = "name";
    }
     
    public static final class Headers {
        public static final String TRACE_ID = "X-Trace-Id";
    }
}

Usage:

CustomerContract.Json.ID
CustomerContract.Headers.TRACE_ID

Extremely readable.

What About Sonar’s “String Literal Repeated X Times”?

This rule is one of my least favorite when applied blindly.

Example:

logger.info("Customer not found");

appearing 4 times.

Sonar:

Extract string literal.

Then you get:

public static final String CUSTOMER_NOT_FOUND = "Customer not found";

Used only for logging.

Now you’ve created an indirection with zero business value.

I’d honestly suppress that finding.

Enterprise Rule of Thumb

I generally classify strings into 5 buckets:

1. Domain Values

ACTIVE
PENDING
APPROVED

✅ Enum

Not constants.

2. Configuration Values

api.url
database.schema

✅ Externalized into properties

Not constants.

3. Technical Contracts

customerId
X-Correlation-Id
Authorization

✅ Constants

4. Repeated Messages

"Customer not found"

⚠️ Usually leave as-is.

Only extract if:

  • localization required
  • true reuse
  • business significance

5. Magic Strings Driving Logic

if ("PREMIUM".equals(type))

✅ Usually enum.

Not constant.

The Litmus Test I Use

Whenever Sonar says:

Extract this repeated string as a constant.

I ask:

Does the constant name convey more meaning than the literal?

If not:

public static final String ACTIVE = "ACTIVE";

adds no value.

If yes:

public static final String HEADER_CORRELATION_ID = "X-Correlation-Id";

adds context and prevents mistakes.

That’s usually the difference between “Sonar-compliant code” and “maintainable enterprise code”. A lot of teams satisfy Sonar by centralizing literals; mature teams focus on ownership, scope, and domain meaning instead of merely reducing duplication. 🤓
