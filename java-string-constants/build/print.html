Java String Constants: Maintainability Over Deduplication

Summary

We started with a broad question about Java string handling, but quickly narrowed it to the more interesting architectural issue: how string literals should be declared, organized, reused, and maintained. The discussion ultimately separated source-code duplication from duplicated knowledge and concluded that maintainability, not literal deduplication, should drive the design.

1. General string-handling practices

We first covered the conventional differences between String, StringBuilder, and StringBuffer. The practical guidance was to use String by default, reserve StringBuilder for repeated construction such as concatenation inside loops, and use StringBuffer only when its synchronization is genuinely needed.

We also reviewed familiar practices such as comparing strings with equals(), using null-safe comparisons, precompiling frequently used regular expressions, using parameterized logging, and avoiding manually concatenated SQL or JSON. However, this turned out not to be the real problem you wanted to explore.

2. The problem with putting every literal in a constants class

You clarified that your concern was not string manipulation, but declaration and organization. SonarQube may recommend extracting repeated literals, but placing all of them in a global Constants or Strings utility class creates a different maintainability problem: a large, unstructured collection with unclear ownership.

We considered organizing constants by context instead, such as ApiHeaders, JsonFields, DatabaseColumns, or domain-specific vocabulary classes. We also established that not every repeated literal deserves extraction. A constant should generally add meaning or represent shared knowledge, rather than merely give a second name to obvious text.

3. Case and formatting variants expose the limits of constants

You then introduced variants such as:

- "active"
- "ACTIVE"
- "Active"
- "is active"
- "is_active"
- "IsActive"
- "IS_ACTIVE"

This demonstrates why constants and enums are not universal solutions. If identifiers are named after their representations, names such as ACTIVE_LOWER, ACTIVE_TITLE, IS_ACTIVE_1, and IS_ACTIVE_2 quickly become awkward and arbitrary.

We distinguished representation variants from genuinely different contracts. For example, isActive in JSON, is_active in a database, and Is Active in a user interface may look related but belong to separate contexts. If they must be centralized, their identifiers should describe their role, such as JSON_IS_ACTIVE, DB_IS_ACTIVE, and LABEL_IS_ACTIVE, rather than merely describing capitalization.

4. A Strings class with identifiers matching their values

You proposed a more direct vocabulary:

public class Strings {
    public final String active = "active";
    public final String ACTIVE = "ACTIVE";
    public final String Active = "Active";
}

The idea is understandable because the identifier mirrors the value, autocomplete works as a dictionary, and there is little conceptual indirection. If implemented, the fields should at least be static final, since creating identical fields for every instance provides no benefit.

The fundamental problem is that Java identifiers cannot faithfully represent every possible string. Both "is active" and "is_active" might naturally map to is_active, causing a collision. Once suffixes or formatting descriptions are introduced to resolve those collisions, the approach loses much of its original naturalness.

5. Classifying strings by what they represent

We stepped back and treated strings according to purpose rather than syntax. User-visible text belongs in resource bundles or another localization system. Configuration belongs in properties, YAML, environment variables, or typed configuration objects. Protocol tokens, JSON names, headers, and database identifiers may belong in narrowly scoped contract classes.

Domain states may be represented by enums or value objects when type safety is valuable, while simple local literals can remain inline. This avoids treating every string as though it belonged to one universal category and prevents the creation of a giant global string registry.

6. Building phrases from atomic word constants

You proposed declaring individual words:

String is = "is";
String active = "active";

and composing phrases with a delimiter:

String.join(SPACE, is, active);

This can be a legitimate pattern for machine-oriented text, especially generated identifiers, paths, keys, queries, or small domain-specific languages. For example, composing customer, address, and city with dots or underscores can be systematic and useful.

It is less suitable for natural language. Human languages differ in word order, agreement, plurality, punctuation, and grammar, so translating individual words and joining them mechanically does not reliably produce correct messages. Human-facing phrases should normally be externalized as complete messages, while technical identifiers may be safely composed from smaller tokens.

7. Whether repeated inline strings are inherently bad

We then returned to the central concern: if a string appears in several places, is leaving it inline necessarily poor practice? The answer was no. Literal duplication is not automatically equivalent to duplicated knowledge.

A repeated HTTP header, serialization key, or external protocol token usually represents one decision that must change consistently, so centralizing it can improve maintainability. Conversely, the same word appearing in several independent logs or local comparisons may simply be repeated text. Extracting it can introduce naming, importing, navigation, and organizational costs without producing a meaningful abstraction.

8. Treating SonarQube as an adviser rather than an authority

The strongest practical conclusion was that SonarQube’s duplicate-string warning should be treated as a review prompt, not an unconditional command. Static analysis can detect matching characters, but it cannot always determine whether those occurrences represent the same concept, contract, or maintenance responsibility.

A useful test is:

If this value changes, should all of these occurrences necessarily change together?

If yes, there is probably duplicated knowledge and a named abstraction may help. If no, extracting the literal may create false coupling. A mature quality profile can therefore retain high-value correctness and security rules while relaxing or lowering the severity of stylistic rules that repeatedly encourage worse designs.

9. How other programming-language communities approach it

We considered Java alongside C#, Python, JavaScript, TypeScript, Go, and Rust. These communities differ in syntax and type systems, but none generally treats every repeated string literal as something that must be deduplicated. Dynamic object literals and dictionaries may make vocabularies feel more natural in JavaScript or Python, while enums and stronger types are more common in Rust and TypeScript.

Across languages, the broader tendency is to centralize shared meaning, contracts, configuration, and domain concepts rather than blindly deduplicating text. Ordinary local literals are widely accepted when they remain understandable and do not create a coordinated-change risk.

10. Java and OpenJDK’s actual direction

Finally, we examined whether Java itself appears to regard source-level string duplication as a language problem. Java has invested in strings, but primarily in runtime efficiency, representation, composition, and readability. Examples include automatic string deduplication in G1, Compact Strings, optimized concatenation, and text blocks.

String templates were explored as a way to improve composition, validation, and embedded expressions, although that proposal was withdrawn rather than becoming the answer to constant organization. We found no apparent OpenJDK roadmap item for automatic named string vocabularies or Sonar-style source-literal deduplication.

Final conclusion

Our conclusion was not that constants are useless or that strings should always be scattered freely. It was that deduplication should follow semantics and maintenance responsibility, not textual equality.

A practical policy would be:

  • Keep local, obvious, independent literals inline.
  • Centralize strings that represent shared contracts or coordinated decisions.
  • Externalize user-facing messages for localization.
  • Use configuration mechanisms for environment-dependent values.
  • Introduce enums or value objects when type safety genuinely simplifies the domain.
  • Avoid universal Constants or Strings dumping grounds.
  • Treat SonarQube’s duplicate-string finding as a question requiring judgment, not as proof of defective code.

In its shortest form:

Repeat text when repetition is harmless; remove duplicated knowledge when the copies must evolve together.

If you’re aiming for real-world Java, clean code, and SonarQube compliance, the biggest mindset shift is:

Don’t optimize strings prematurely. Optimize based on usage patterns.

A lot of Java string advice is 15+ years old and no longer fully applies on modern JVMs.

1. Understand the 3 Main Types

String

Immutable.

String name = "Luis";
name = name + " Garcia";

Every modification creates a new String.

Use when:

  • Value rarely changes
  • DTOs
  • Configuration values
  • Method parameters
  • Return values
  • Domain objects

✅ Default choice

StringBuilder

Mutable.

StringBuilder sb = new StringBuilder();
sb.append("Hello");
sb.append(" ");
sb.append("World");
String result = sb.toString();

Use when:

  • Building text incrementally
  • Loops
  • CSV generation
  • SQL construction
  • Log message construction

✅ Preferred for repeated modifications

StringBuffer

Thread-safe version of StringBuilder.

StringBuffer sb = new StringBuffer();

Use only when:

  • Multiple threads truly share the same buffer

In modern code this is uncommon.

✅ Rarely needed today

Sonar also generally prefers StringBuilder when synchronization isn’t required. [stackoverflow.com], [community….source.com]

2. Modern Best Practice: String Concatenation

Good

String message = firstName + " " + lastName;

For small concatenations:

String title = "User: " + username;

Modern JVMs optimize this very effectively.

Don’t write

StringBuilder sb = new StringBuilder();
sb.append(firstName);
sb.append(" ");
sb.append(lastName);

just to be “efficient”.

That hurts readability.

3. Where StringBuilder REALLY Matters

Bad

String result = "";
for (User user : users) {
    result += user.getName();
}

Why?

Each iteration creates a new String.

Complexity grows badly.

Good

StringBuilder result = new StringBuilder();
for (User user : users) {
    result.append(user.getName());
}
return result.toString();

This is one of the most common Sonar recommendations. [community….source.com], [community….source.com]

4. Compare Strings Correctly

Wrong

if (str1 == str2)

== compares references.

Correct

if (str1.equals(str2))

Null-safe

if ("ACTIVE".equals(status))

instead of

if (status.equals("ACTIVE"))

because:

status = null;

would throw:

NullPointerException

5. Use isBlank() Instead of Ugly Checks

Old

if (str == null || str.trim().isEmpty())

Modern

if (str == null || str.isBlank())

Java 11+

Much cleaner.

6. Use String.join()

Bad

String csv =
    firstName + "," +
    lastName + "," +
    city;

Better

String csv = String.join(
    ",",
    firstName,
    lastName,
    city
);

Cleaner and easier to maintain.

7. Use Formatting Methods

Old

String message =
    "User " + userId +
    " has balance " + balance;

Better

String message =
    "User %s has balance %.2f"
        .formatted(userId, balance);

Java 15+

Or

String.format(...)

8. Avoid Magic Case Conversion

Dangerous

if (str.toLowerCase().equals("admin"))

Locale issues can occur.

Better

if ("admin".equalsIgnoreCase(str))

9. Avoid Repeated Regex Compilation

Bad

public boolean isValid(String s) {
    return s.matches("[A-Z]{3}[0-9]{5}");
}

Called thousands of times?

Regex gets recompiled repeatedly.

Better

private static final Pattern PATTERN =
    Pattern.compile("[A-Z]{3}[0-9]{5}");

public boolean isValid(String s) {
    return PATTERN.matcher(s).matches();
}

Real performance improvement.

10. StringBuilder Capacity

Rarely discussed.

If you know size beforehand:

StringBuilder sb = new StringBuilder(5000);

instead of:

StringBuilder sb = new StringBuilder();

Useful for:

  • CSV exports
  • Report generation
  • Large JSON construction

Reduces internal reallocations.

11. Don’t Compare StringBuilder Objects

Many developers get caught here.

StringBuilder sb1 = new StringBuilder("abc");
StringBuilder sb2 = new StringBuilder("abc");
sb1.equals(sb2);

Result:

false

StringBuilder doesn’t compare content through equals(). [stackoverflow.com], [javathinking.com]

Use:

sb1.toString().equals(sb2.toString())

12. Real Enterprise Patterns

Logging

Bad:

logger.info(
    "User " + user.getId() +
    " logged in"
);

If log level is disabled:

  • String still gets created.

Better:

logger.info(
    "User {} logged in",
    user.getId()
);

SLF4J evaluates lazily.

Huge win in enterprise applications.

SQL

Bad:

String sql =
    "SELECT * FROM users WHERE id = " + id;

SQL Injection risk.

Better:

PreparedStatement ps =
    connection.prepareStatement(
        "SELECT * FROM users WHERE id = ?"
    );

JSON

Bad:

vString json =
    "{"name":"" + name + ""}";

Use:

  • Jackson

  • Gson

  • JSON-B

Never manually build production JSON.

A common anti-pattern:

public static final String YES = "YES";

My Rule

If the literal itself is the business meaning:

"ACTIVE"
"INACTIVE"
"PENDING"

➡️ Consider an enum instead.

    ACTIVE,
    INACTIVE,
    PENDING
}

Where Constants Actually Make Sense

I usually ask:

“Would changing this value require changing multiple places?”

If yes → constant.

Good Candidate #1: Regex

private static final Pattern EMAIL_PATTERN = Pattern.compile(...);

Makes sense.

Regexes are difficult to understand and likely reused.

Good Candidate #2: JSON Keys

Good Candidate #4: External Contract Values

These strings represent a contract.

That’s important.

├─ CustomerService
├─ CustomerRepository

For larger domains:

public final class CustomerContract {
 
    private CustomerContract() {}
     
    public static final class Json {
        public static final String ID = "id";
        public static final String NAME = "name";
    }
     
    public static final class Headers {
        public static final String TRACE_ID = "X-Trace-Id";
    }
}

Usage:

CustomerContract.Json.ID
CustomerContract.Headers.TRACE_ID

Extremely readable.

Whenever Sonar says:

Extract this repeated string as a constant.

I ask:

Does the constant name convey more meaning than the literal?

If not:

Sonar’s duplicate-string rule is often correct for:

"userId"
"customerId"
"x-request-id"

but often harmful for:

"ACTIVE"
"PENDING"
"Save"
"Cancel"
"Error"

because developers start fighting the tool instead of modeling the domain.

When you reach:

ACTIVE_CAPITALIZED
ACTIVE_LOWERCASE

that’s usually a sign that constants are the wrong abstraction.

  • a message bundle

Question 4

Look, I know the enum with utility methods may be the most accptable solution for this.
But it doesn't feel natural, you know?
Why not have plain old simple strings like this?

public class Strings {
    public final String active = "active";
    public final String ACTIVE = "ACTIVE";
    public final String Active = "Active";
    public final String is_active = "is active"; // I know, can collide with "is_active"
    public final String IS_ACTIVE = "IS ACTIVE";

Honestly? From a language design perspective, what you’re proposing is actually quite reasonable.

The problem is that Java’s identifier rules weren’t designed for this use case.

When you write:

public class Strings {
    public final String active = "active";
    public final String ACTIVE = "ACTIVE";
    public final String Active = "Active";
}

you’re essentially trying to create a string dictionary where:

  • the field name mirrors the value
  • auto-completion becomes the lookup mechanism
  • the compiler provides type safety

That’s not crazy at all.

The issue is that Java identifiers are case-sensitive but otherwise limited, so eventually you hit collisions:

is_active = "is active";
is_active = "is_active"; // impossible

and then the naming scheme falls apart.

What’s interesting is that many languages moved away from this pattern

For example, your Strings class is trying to act like:

{
  "active": "active",
  "ACTIVE": "ACTIVE",
  "Active": "Active",
  "is active": "is active",
  "is_active": "is_active"
}

which is really a dictionary/map, not a class.

In a language with first-class module constants this feels natural.

In Java, not so much.

The real objection I’d have is not the naming

It’s the instantiation.

I’d never write:

public class Strings {
    public final String active = "active";
}

because every instance creates fields that are identical.

I’d at least make them static:

public final class Strings {
    private Strings() {}
    public static final String active = "active";
    public static final String ACTIVE = "ACTIVE";
    public static final String Active = "Active";
}

Even though the names break Java conventions.

But here’s where things get philosophical

Suppose I read:

if (status.equals(Strings.active))

What did I gain?

Compared to:

if (status.equals("active"))

Almost nothing.

In fact, I arguably lost readability because:

  • "active" is immediately understandable
  • Strings.active requires navigation

That’s why many senior developers resist extracting simple literals.

The Real Cost of Constants

A lot of developers only consider the benefit:

  • Finding them
  • Importing them
  • Organizing them
  • Maintaining them
  • Explaining them

Abstractions are not free.

The caveat is that the opposite extreme is also bad:

✅ “Centralize strings that represent contracts, protocols, configuration keys, field names, or shared business rules.”

Question 11

And, do you know if Java really cares about this, like having something in its roadmap to deal with it?

I’ll check the current OpenJDK roadmap and recent JEPs, separating language-level string features from JVM storage optimizations.As of October 2026, I could not find an active or proposed OpenJDK feature intended to solve source-code string-literal duplication or provide a more natural “string vocabulary/constants” construct.

The current OpenJDK JEP Index includes upcoming language and JVM work, but nothing resembling automatic declaration of named string constants, compile-time literal vocabularies, or Sonar-style source-code deduplication. [openjdk.org]

Java cares about strings, but at different levels

1. Runtime memory duplication

Java has tackled duplicate string storage. JEP 192: String Deduplication in G1 introduced automatic deduplication of equal strings’ backing character arrays under G1. Importantly, it explicitly requires no changes to application code. [openjdk.org]

Java also introduced Compact Strings, which changed String internally to use a more space-efficient representation where possible, without changing its public API. [openjdk.org]

So the JVM’s philosophy is roughly:

If identical strings waste memory, let the runtime optimize them rather than forcing programmers to construct elaborate constant catalogs.

That is separate from maintainability and SonarQube’s repeated-literal rule.

2. Concatenation performance

JEP 280: Indify String Concatenation changed how javac represents concatenation, allowing the runtime to optimize it without requiring developers to manually rewrite ordinary concatenations as StringBuilder chains. [openjdk.org]

Again, the direction is:

Write understandable source code; let the compiler and JVM improve its execution.

3. Multiline strings

Java introduced text blocks through Project Amber to make multiline strings more readable. The current Project Amber page lists text blocks among its delivered features. [openjdk.org]

That improves declaration ergonomics:

String query = """
        SELECT id, name
        FROM customer
        WHERE active = true
        """;

But it does not attempt to deduplicate literals.

4. String composition

String templates were previewed in JDK 21 and 22. Their stated goals included making strings containing computed values more readable and enabling validation for content such as SQL, XML, and JSON. They were not designed to address repeated literals or constant organization. [openjdk.org], [openjdk.org]

More importantly, the proposed third preview, JEP 465, is currently listed by Project Amber as withdrawn. [openjdk.org]

Therefore, string templates should not currently be treated as Java’s forthcoming answer to string handling.

What this tells us

Java clearly invests in:

  • string memory representation;
  • runtime deduplication;
  • concatenation performance;
  • readable multiline strings;
  • safer and clearer string composition.

But Java does not appear to treat repeated source literals as a language-design problem.

There is no apparent roadmap toward syntax such as:

vocabulary Status {
    "active";
    "ACTIVE";
    "Active";
}

or:

symbol active; // automatically means "active"

That supports your intuition: the language designers do not seem to consider Sonar-style literal deduplication important enough to warrant new syntax.

The practical conclusion

Sonar’s duplicated-string rule is a static-analysis maintainability heuristic. It is not a Java language requirement, JVM requirement, or apparent OpenJDK design priority.

A sensible team policy would be:

Repeated text alone is not sufficient reason to introduce a constant. Extract it when the occurrences represent the same shared knowledge and must evolve together.

For example:

if ("active".equals(status)) {
    log.debug("Customer is active");
}

Having "active" elsewhere is not automatically a design defect.

By contrast:

request.setHeader("X-Correlation-Id", id);

repeated across many HTTP components probably represents one shared protocol decision, so a scoped constant is appropriate:

final class RequestHeaders {
    static final String CORRELATION_ID = "X-Correlation-Id";
    private RequestHeaders() {}
}

Bottom line

No, Java does not currently appear to have a roadmap item specifically addressing the declaration or deduplication of source-level string constants. Java’s development has concentrated on making strings more efficient, expressive, and safe, while leaving semantic organization to application design.

So I would not design a complicated string framework in anticipation of Java “solving” this later. Keep obvious literals inline, centralize actual shared contracts, and tune or downgrade the Sonar rule when it consistently produces worse code.
