I’ll check the current OpenJDK roadmap and recent JEPs, separating language-level string features from JVM storage optimizations.As of **October 2026**, I could not find an active or proposed OpenJDK feature intended to solve **source-code string-literal duplication** or provide a more natural “string vocabulary/constants” construct.

The current OpenJDK JEP Index includes upcoming language and JVM work, but nothing resembling automatic declaration of named string constants, compile-time literal vocabularies, or Sonar-style source-code deduplication. [[openjdk.org]](https://openjdk.org/jeps/0)

## Java cares about strings, but at different levels

### 1. Runtime memory duplication

Java has tackled duplicate string **storage**. JEP 192: String Deduplication in G1 introduced automatic deduplication of equal strings’ backing character arrays under G1. Importantly, it explicitly requires **no changes to application code**. [[openjdk.org]](https://openjdk.org/jeps/192)

Java also introduced Compact Strings, which changed `String` internally to use a more space-efficient representation where possible, without changing its public API. [[openjdk.org]](https://openjdk.org/jeps/254)

So the JVM’s philosophy is roughly:

> If identical strings waste memory, let the runtime optimize them rather than forcing programmers to construct elaborate constant catalogs.

That is separate from maintainability and SonarQube’s repeated-literal rule.

### 2. Concatenation performance

JEP 280: Indify String Concatenation changed how `javac` represents concatenation, allowing the runtime to optimize it without requiring developers to manually rewrite ordinary concatenations as `StringBuilder` chains. [[openjdk.org]](https://openjdk.org/jeps/280)

Again, the direction is:

> Write understandable source code; let the compiler and JVM improve its execution.

### 3. Multiline strings

Java introduced text blocks through Project Amber to make multiline strings more readable. The current Project Amber page lists text blocks among its delivered features. [[openjdk.org]](https://openjdk.org/projects/amber/)

That improves declaration ergonomics:

```Java
String query = """
        SELECT id, name
        FROM customer
        WHERE active = true
        """;
```

But it does not attempt to deduplicate literals.

### 4. String composition

String templates were previewed in JDK 21 and 22. Their stated goals included making strings containing computed values more readable and enabling validation for content such as SQL, XML, and JSON. They were **not** designed to address repeated literals or constant organization. [[openjdk.org]](https://openjdk.org/jeps/459), [[openjdk.org]](https://openjdk.org/jeps/430)

More importantly, the proposed third preview, JEP 465, is currently listed by Project Amber as **withdrawn**. [[openjdk.org]](https://openjdk.org/projects/amber/)

Therefore, string templates should not currently be treated as Java’s forthcoming answer to string handling.

## What this tells us

Java clearly invests in:

- string memory representation;
- runtime deduplication;
- concatenation performance;
- readable multiline strings;
- safer and clearer string composition.

But Java does **not appear to treat repeated source literals as a language-design problem**.

There is no apparent roadmap toward syntax such as:

```Java
vocabulary Status {
    "active";
    "ACTIVE";
    "Active";
}
```

or:

```Java
symbol active; // automatically means "active"
```

That supports your intuition: **the language designers do not seem to consider Sonar-style literal deduplication important enough to warrant new syntax**.

## The practical conclusion

Sonar’s duplicated-string rule is a static-analysis maintainability heuristic. It is not a Java language requirement, JVM requirement, or apparent OpenJDK design priority.

A sensible team policy would be:

> Repeated text alone is not sufficient reason to introduce a constant. Extract it when the occurrences represent the same shared knowledge and must evolve together.

For example:

```Java
if ("active".equals(status)) {
    log.debug("Customer is active");
}
```

Having `"active"` elsewhere is not automatically a design defect.

By contrast:

```Java
request.setHeader("X-Correlation-Id", id);
```

repeated across many HTTP components probably represents one shared protocol decision, so a scoped constant is appropriate:

```Java
final class RequestHeaders {
    static final String CORRELATION_ID = "X-Correlation-Id";
    private RequestHeaders() {}
}
```

### Bottom line

**No, Java does not currently appear to have a roadmap item specifically addressing the declaration or deduplication of source-level string constants.** Java’s development has concentrated on making strings more efficient, expressive, and safe, while leaving semantic organization to application design.

So I would not design a complicated string framework in anticipation of Java “solving” this later. Keep obvious literals inline, centralize actual shared contracts, and tune or downgrade the Sonar rule when it consistently produces worse code.
