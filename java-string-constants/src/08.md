```
Sure, there's many ways to deal with this, but...
Is there a better way than the usual recommendation to define string constants?
Or should we just ignore SonarQube's nagging of "de-duplicating" strings and just be careful on their handling?
```

---

Honestly?

**Yes, in many cases you should ignore SonarQube's de-duplication nagging.**

That's not being reckless. That's understanding the difference between a **heuristic** and a **design principle**.

---

## The fundamental flaw in "duplicate string" detection

Sonar sees:

```Java
if ("ACTIVE".equals(statusA))
```

and

```Java
if ("ACTIVE".equals(statusB))
```

and thinks:

> Same literal appears twice → extract constant.

But Sonar cannot know:

```Java
"ACTIVE"
```

might be:

- a domain value
- a protocol token
- a one-off comparison
- a business concept
- just plain text

All it sees is duplication.

Humans see intent.

---

## Compare with another famous rule

Imagine Sonar had a rule:

> You repeated the number `2` five times.

Should you do this?

```Java
private static final int TWO = 2;
```

Of course not.

Why?

Because:

```Java
2
```

already communicates perfectly.

---

The same is true for many strings.

```Java
","
":"
"ACTIVE"
"ERROR"
"true"
```

can sometimes be clearer than:

```Java
Constants.COMMA
Constants.COLON
Constants.ACTIVE
Constants.ERROR
Constants.TRUE
```

---

# The real criterion

Not:

> Is this duplicated?

But:

> Is this duplicated knowledge?

That's a huge difference.

---

### Bad duplication (extract)

```Java
"X-Correlation-Id"
```

used in 25 classes.

That's one piece of knowledge.

If the contract changes:

```Java
"Correlation-Id"
```

everything must change.

This deserves a constant.

---

### Good duplication (leave alone)

```Java
logger.warn("Customer not found");
```

used 4 times.

Those aren't necessarily the same knowledge.

They're just the same words.

---

### Ambiguous duplication

```Java
"ACTIVE"
```

This is where judgment is required.

---

# What experienced teams often do

Many teams gradually tune Sonar.

For example:

- Keep security rules.
- Keep bug detection.
- Keep NPE detection.
- Keep resource leak detection.

But relax:

- duplicate string thresholds
- naming nitpicks
- cosmetic recommendations

Because otherwise people start coding for Sonar rather than coding for maintainability.

# The Rule I Like

I tell developers:

Extract a String if **at least one** is true:

### 1. It represents a contract

```Java
"Authorization"
"Content-Type"
"customer_id"
```

✅ extract

---

### 2. It is likely to change

```Java

```

✅ extract

---

### 3. It has non-obvious meaning

```Java

```

✅ extract

---

### 4. It is central to the domain

```Java

```

✅ maybe enum/value object

---

Otherwise:

```Java

"PENDING"
","
":"
" "
"yes"
"no"
```

often stay inline.

# So, is there a "better way"?

After years of enterprise Java, my answer is:

> No, there is no universal better way than constants.

The better solution is **being selective about what deserves a constant**.

The biggest mistake isn't leaving strings inline.

The biggest mistake is extracting every duplicated literal into a constant and ending up with:

```Java
Constants.ACTIVE
Constants.ACTIVE_LOWER
Constants.IS_ACTIVE
Constants.SPACE
Constants.COLON
Constants.EMPTY_STRING
```

which makes the codebase harder to understand than the original literals ever were.

So if I had to give a practical rule:

✅ Treat Sonar's duplicate-string warning as a **suggestion**.

✅ Extract strings that represent **contracts, configuration, or shared business concepts**.

✅ Ignore the warning when extracting the string would not improve the meaning of the code.

That's one of those rare cases where "Sonar-compliant" and "maintainable" are not always the same thing.
