This is actually a surprisingly deep software architecture topic.

I think you've already stumbled upon the core insight:

> The problem is not "how do I declare strings?"
> 
> The problem is "what kind of information does a string represent?"

Many teams end up with a giant constants jungle because Java historically treated all string literals the same, while in reality they belong to very different categories.

# Why Java feels awkward

Java constants have always relied on:

```Java
public static final String SOMETHING
```

which means:

- identifier must be unique
- identifier must be legal Java
- identifier can't contain spaces
- naming convention expects screaming snake case

but string values often need:

```Java
"active"
"ACTIVE"
"Active"
"is active"
"is_active"
"IsActive"
```

Those worlds don't align.

# My Current Favorite Approach

Not enums.

Not a giant constants class.

Use **typed vocabularies**.

Example:

```Java
public final class CustomerFields {

    private CustomerFields() {}

    public static final String JSON_IS_ACTIVE = "isActive";
    public static final String DB_IS_ACTIVE = "is_active";
    public static final String UI_IS_ACTIVE = "Is Active";

}
```

Notice what changed.

The identifier describes the **purpose**, not the text.

# Even Better: Externalize When the Text Is Content

This is where I think many Java applications go wrong.

Suppose:

```Java
"Save"
"Cancel"
"Customer not found"
```

These are not constants.

These are messages.

---

Instead of:

```Java
public static final String SAVE = "Save";
```

use:

```properties
button.save=Save
button.cancel=Cancel
```

Java:

```Java
ResourceBundle bundle = ResourceBundle.getBundle("messages");
bundle.getString("button.save");
```

Now you automatically get:

```properties
button.save=Guardar
```

for Spanish.

# If You're Fighting Sonar...

This might be controversial.

Many teams should simply reconfigure the rule.

```Java

Developer:

```

Everybody loses.

A principle I use:

### Extract only if the constant name teaches me something.

Bad:

```Java

```

Good:

```Java
public static final String CUSTOMER_STATUS_ACTIVE = "ACTIVE";
```

because now the constant expresses domain meaning.

# The Future Direction

If I were starting a greenfield Java project today, I would classify strings into exactly these groups:

|Category|Storage|
|---|---|
|UI text|Resource bundle / I18n|
|Configuration|YAML / properties|
|API contracts|Vocabulary classes|
|DB columns|Column classes|
|JSON fields|Field classes|
|Domain states|Enums|
|Temporary literals|Inline strings|
|Repeated business constants|Scoped constant classes|

Notice what's missing:

```Java
Constants.java
```

I would actively ban it.

# My Honest Conclusion

After working through your examples, I don't actually think the best solution is "better constants."

I think the best solution is realizing that **"string" is not a single category of thing**.

The industry historically tried:

```Java
public final class Constants
```

Then moved to:

```Java
Enums everywhere
```

And neither is fully satisfactory.

The most maintainable systems I've seen treat strings according to their role:

- text → I18n resources
- configuration → config files
- contracts → vocabulary classes
- states → enums
- identifiers → records/value objects
- one-off values → inline literals

Once you do that, the number of actual string constants in Java code drops dramatically, and the remaining ones become much easier to organize naturally. The paradox is that the best way to manage string constants is often to stop treating everything as a string constant in the first place. 🤓
