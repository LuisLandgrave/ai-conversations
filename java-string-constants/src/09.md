```
And what does Java or Oracle recommend?
Or maybe those many Java rockstars out there just don't care because we shouldn't be making a big deal out of this?
```

---

This is one of those topics where the Java community has quietly converged on an answer over the last 20 years:

> **Don't overthink string constants.**
> 
> Model concepts properly, extract only meaningful constants, and don't blindly obey duplication warnings.

And that's not just my opinion. It's roughly where much of the Java ecosystem ended up.

---

## What Oracle/Java Actually Says

Interestingly, Oracle never really published a grand doctrine saying:

> "All repeated strings must be constants."

Instead, Java's language features suggest a more nuanced approach:

- `public static final` for true constants
- `enum` for fixed value sets
- `ResourceBundle` for localizable text
- properties/YAML for configuration
- ordinary string literals when they're simply literals

In other words:

> Java gives you several tools because different strings represent different things.

---

## What Effective Java Says

If there's one book that influenced modern Java style the most, it's **Joshua Bloch's Effective Java**.

Bloch heavily criticized the old "constant interface" pattern and recommended putting constants in classes where they logically belong, not creating global dumping grounds. [[codeql.github.com]](https://codeql.github.com/codeql-query-help/java/java-constants-only-interface/), [[stackoverflow.com]](https://stackoverflow.com/questions/2659593/what-is-the-use-of-interface-constants)

Notice what's missing:

- No "extract every duplicate string."
- No "never use string literals."
- No "create Constants.java for everything."

## What Most Java Rockstars Actually Do

If you look at code from:

- Spring
- Hibernate
- Jackson
- Apache Commons
- JDK itself

you'll find plenty of this:

```Java
if ("UTF-8".equals(name))
```
```Java
if ("application/json".equals(contentType))
```
```Java
if ("GET".equals(method))
```

You do **not** see:

```Java
public static final String GET = "GET";
public static final String POST = "POST";
public static final String PUT = "PUT";
```

everywhere.

Why?

Because sometimes the literal is clearer than the constant.

## The Industry Shift

Years ago the thinking was:

```
Repeated literal = evil
```

Today the thinking is closer to:

```
Repeated knowledge = evil
Repeated text = maybe fine
```

That distinction matters enormously.

---

### Example 1

```Java
if ("ACTIVE".equals(status))
```

in three places.

Many modern Java developers leave it exactly like that.

---

### Example 2

```Java
header.get("X-Correlation-Id")
```

in three places.

Most developers extract it.

Because it's a contract.

## Why Sonar Sometimes Feels Wrong

Static analyzers work on patterns.

Humans work on semantics.

Sonar sees:

```Java
"ACTIVE"
```

repeated five times.

You see:

```Java
ACTIVE
```

as an obvious business term.

Sonar cannot distinguish those situations reliably.

That's why many mature teams adjust rule severity.

## If I Were Writing a Coding Standard Today

I'd say:

### Inline literals are acceptable when:

```Java
"ACTIVE"
"PENDING"
"ERROR"
"GET"
"POST"
","
":"
" "
```

are obvious and local.

---

### Constants are appropriate when:

```Java
"X-Correlation-Id"
"customer_reference_id"
"/api/v3/customers"
```

represent contracts or shared knowledge.

---

### Enums are appropriate when:

```Java
ACTIVE
INACTIVE
PENDING
APPROVED
```

represent states.

---

### Resource bundles are appropriate when:

```Java
"Customer not found"
"Save"
"Cancel"
```

are user-facing text.

## My honest conclusion

After decades of Java, I don't think the community found a magical replacement for string constants.

Instead, the community gradually realized something simpler:

> **String de-duplication is not a goal. Maintainability is.**

So if your question is:

> _"Should I spend lots of effort inventing sophisticated mechanisms to avoid repeating string literals?"_

I'd answer:

**Usually no.**

If your question is:

> _"Should I completely ignore Sonar's duplicate-string warnings?"_

I'd answer:

**Treat them as code-review suggestions, not laws.**

The "Java rockstars" you're referring to generally care much more about:

- API design
- immutability
- type safety
- testing
- readability

than about whether `"ACTIVE"` appears three times in a codebase.

That may be the biggest lesson here: the community largely stopped treating duplicate string literals as a major architectural problem unless those literals represent a shared contract or a domain concept that genuinely benefits from centralization. 🤓
