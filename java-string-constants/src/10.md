```
That's what I thought! The keyword here is "maintainability".
Having a complicated way to define and handle strings is hard to maintain.
Just using them freely whenever they're needed without worrying should suffice!
And my gut tells me not many other programming languages really care about strings de-duplication...
Am I right? Please enlighten me or correct me if I'm wrong
```

---

Your gut is actually pretty well aligned with where most mature software communities have landed.

The important nuance is:

> **Most languages don't care much about string de-duplication. They care about de-duplicating meaning.**

Those are very different things.

---

## Let's look around the industry

### Java

You'll often see:

```Java
if ("ACTIVE".equals(status))
```

and

```Java
jsonNode.get("customerId")
```

all over production code.

Despite what static analyzers may suggest.

The best Java developers tend to ask:

> Is this a shared contract?

before extracting a constant.

Not:

> Has this literal appeared 3 times?

---

### C#

The .NET world arguably cares even less.

It's very common to see:

```C#
if (status == "ACTIVE")
```

or:

```C#
builder.Property("customerId");
```

Unless the string represents:

- configuration
- protocol values
- API contracts
- database identifiers

many teams leave them inline.

---

### Python

Python developers are probably the least concerned.

You'll frequently find:

```Python
if status == "active":
```

in excellent production code.

The Python philosophy generally values readability over abstraction.

A common Python reaction would be:

> Why introduce a constant if the literal is clearer?

---

### JavaScript / TypeScript

This is an interesting middle ground.

Developers often create objects:

```TypeScript
const Status = {
    ACTIVE: "ACTIVE",
    PENDING: "PENDING"
};
```

but usually for:

- autocomplete
- avoiding typos
- type checking

not because duplication itself is considered evil.

---

### Go

Go developers are famously pragmatic.

You'll see:

```Go
if status == "active" {
}
```

everywhere.

Constants appear when:

```Go
const HeaderAuthorization = "Authorization"
```

represents a shared contract.

---

### Rust

Rust often uses enums and stronger typing.

But even there, people don't extract every repeated string.

The preference is usually:

```Rust
enum Status {
    Active,
    Pending,
}
```

rather than endless string constants.

# Why Duplication Became Such a Big Deal Historically

A lot of this comes from older software engineering culture.

Back in the 90s and early 2000s:

```Java
"ACTIVE"
```

appeared in twenty files.

Changing it meant manually searching the codebase.

Refactoring tools weren't nearly as powerful.

So developers developed a reflex:

> Every repeated value must have one source of truth.

Today:

- IntelliJ
- Eclipse
- VS Code
- Rider

can refactor huge codebases safely.

The cost-benefit calculation has changed.

---

# Where Your Maintainability Argument Is Strong

Consider:

```Java
private static final String ACTIVE = "ACTIVE";
private static final String ACTIVE_TITLE = "Active";
private static final String ACTIVE_LOWER = "active";
private static final String ACTIVE_LABEL = "Active";
```

Now I have:

- Extra files
- Extra symbols
- Extra navigation
- Extra naming decisions

all to avoid writing:

```Java
"ACTIVE"
```

a few times.

That's often negative maintainability.

---

# The DRY Principle Is Frequently Misunderstood

People think DRY means:

> Never repeat text.

The original idea was closer to:

> Never repeat knowledge.

These are not equivalent.

---

Example:

### Repeated text

```Java
logger.info("Customer not found");
```

three times.

Not necessarily a problem.

---

### Repeated knowledge

```Java
"X-Correlation-Id"
```

used in fifteen services.

Definitely a problem.

Because a change must be synchronized everywhere.

---

# The Real Cost of Constants

A lot of developers only consider the benefit:

```Java
Constants.ACTIVE
```

But there are costs:

- Naming things
- Finding them
- Importing them
- Organizing them
- Maintaining them
- Explaining them

Abstractions are not free.

This is one of the central lessons from software architecture.

---

# My Rule of Thumb

I usually ask:

### Does this string define a contract?

```Java
"Authorization"
"customer_id"
"/api/v1/orders"
```

Extract it.

---

### Does this string define a domain concept?

```Java
ACTIVE
INACTIVE
```

Consider an enum.

---

### Is this just readable text?

```Java
"Active"
"Customer not found"
","
":"
```

Leave it alone unless there's another reason.

---

# So Are You Wrong?

Honestly?

Not really.

I think you're converging toward the position many experienced developers eventually reach:

> **Excessive string de-duplication often harms maintainability more than it helps.**

The caveat is that the opposite extreme is also bad:

```Java
"customer_id"
"customer_id"
"customer_id"
"customer_id"
```

scattered across 40 modules.

That is shared knowledge and deserves centralization.

So I'd slightly refine your statement:

✅ "Just use strings freely when they are local, obvious, and readable."

✅ "Centralize strings that represent contracts, protocols, configuration keys, field names, or shared business rules."

❌ "Deduplicate every repeated literal because Sonar says so."

In my experience, that's much closer to how high-quality codebases evolve across Java, C#, Python, Go, TypeScript, and other mainstream languages than strict, dogmatic string-constant extraction.
