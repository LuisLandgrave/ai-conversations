```
Yes, using enumerations is one painful way to deal with them...
But there must be better ways to put them all those string constants together ina structured way.
Let me just give you one example where constants or enums are NOT a fit-for-all solution:
    Imagine I need a string constant "active" and ALSO "ACTIVE"; I know you'll say "you can just name 
    one ACTIVE and the other one ACTIVE_1 or ACTIVE_ALLCAPS...
    But then, imagine we ALSO need to use "Active".
    And then, it gets worse... Imagine we need longer strings, delimiter (space) separated!
    For example:
        IS_ACTIVE = "is active", and then ISACTIVE = "IsActive",
        and then IS_ACTIVE = "is active",
        and then any sort of combinations (like: IS_ACTIVE1 = "is active" and IS_ACTIVE2 = "is_active")
        that just go down the rabbit hole...
```

---

Now we're getting into what I consider one of the biggest flaws of many Java coding standards.

You're describing a situation where **the problem isn't duplicate strings**, it's that **the string itself is the data**.

For example:

```Java
"active"
"ACTIVE"
"Active"
"is active"
"is_active"
"IsActive"
"IS_ACTIVE"
```

Trying to force these into constants leads to nonsense:

```Java
ACTIVE_LOWER
ACTIVE_UPPER
ACTIVE_PASCAL
ACTIVE_TITLE
ACTIVE_SNAKE
ACTIVE_SNAKE_UPPER
```

At that point you've lost all readability.

---

## The underlying question is:

**Why do these strings exist?**

There are usually 4 distinct cases.

### Case 1: Representation Variants

Suppose all of these mean the same thing:

```Java
"active"
"ACTIVE"
"Active"
```

Then these should not be independent constants.

Instead:

```Java
enum Status {
    ACTIVE
}
```

And provide formatting methods:

```Java
public enum Status {

    ACTIVE;

    public String lowerCase() {
        return name().toLowerCase();
    }

    public String titleCase() {
        return "Active";
    }

    public String upperCase() {
        return name();
    }

}
```

Usage:

```Java
Status.ACTIVE.lowerCase();
Status.ACTIVE.upperCase();
Status.ACTIVE.titleCase();
```

Now the _concept_ is centralized, not every possible representation.

---

### Case 2: Contract Strings

These are things like:

```Java
"isActive"      // JSON
"is_active"     // DB
"IS_ACTIVE"     // CSV
"Is Active"     // UI
```

These are actually different contracts.

I would model them as:

```Java
public final class CustomerFields {

    public static final String JSON_IS_ACTIVE = "isActive";
    public static final String DB_IS_ACTIVE = "is_active";
    public static final String CSV_IS_ACTIVE = "IS_ACTIVE";
    public static final String LABEL_IS_ACTIVE = "Is Active";

}
```

Notice the naming.

The meaning is:

```Java
IS_ACTIVE
```

The representation changes by context.

---

### Case 3: UI Text

The worst thing I see in enterprise apps:

```Java
public static final String SAVE = "Save";
public static final String CANCEL = "Cancel";
public static final String YES = "Yes";
```

These should not be constants.

These should be messages.

```properties
button.save=Save
button.cancel=Cancel
```

or

```YAML
button:
  save: Save
  cancel: Cancel
```

Because eventually:

```properties
button.save=Guardar
```

becomes necessary.

---

### Case 4: Parser / Mapper Domains

This is probably closest to your example.

Imagine incoming data:

```Java
ACTIVE
active
Active
A
1
```

all mean the same thing.

The solution isn't constants.

The solution is normalization.

```Java
private static final Map<String, Status> STATUS_MAPPING =
        Map.of(
            "ACTIVE", Status.ACTIVE,
            "active", Status.ACTIVE,
            "Active", Status.ACTIVE,
            "A", Status.ACTIVE,
            "1", Status.ACTIVE
        );
```

Now business code never sees string literals.

---

# What I See Good Teams Doing

Instead of:

```Java
GlobalConstants.java
```

they create **vocabularies**.

Example:

```Java
CustomerVocabulary
OrderVocabulary
JsonFields
ApiContract
DatabaseFields
```

Because the problem isn't duplication.

The problem is that every string belongs to a language.

Example:

```Java
public final class CustomerJson {
    public static final String IS_ACTIVE = "isActive";
    public static final String FIRST_NAME = "firstName";
    public static final String LAST_NAME = "lastName";
}
```

Usage:

```Java
CustomerJson.IS_ACTIVE
```

Immediately tells me:

- meaning → IS_ACTIVE
- representation → JSON

# My Personal Hot Take 🔥

Sonar's duplicate-string rule is often correct for:

```Java
"userId"
"customerId"
"x-request-id"
```

but often harmful for:

```Java
"ACTIVE"
"PENDING"
"Save"
"Cancel"
"Error"
```

because developers start fighting the tool instead of modeling the domain.

When you reach:

```Java
ACTIVE_UPPERCASE
ACTIVE_CAPITALIZED
ACTIVE_LOWERCASE
ACTIVE_UNDERSCORE
ACTIVE_SPACE_SEPARATED
```

that's usually a sign that **constants are the wrong abstraction**.

The real abstraction is one of:

- an enum
- a message bundle
- a vocabulary/contract class
- a formatter
- a mapper/normalizer

depending on why those strings differ.

The most maintainable systems I've seen don't organize strings by **syntax** ("all constants here"), they organize strings by **ownership and context** ("these are JSON field names", "these are DB columns", "these are UI labels", "these are legal status values"). That's the point where the rabbit hole usually disappears. 🧠
