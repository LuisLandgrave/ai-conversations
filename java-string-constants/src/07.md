```
Now, I go back to the original question: Is there a better way to declare string constants in Java?
Because it's like if I just use them in the code, it's just bad when I need to write them in many places... Right?
```
---

Short answer:

> **Yes, but probably not in the way most Java developers think.**

I think the industry spent years debating between:

```Java
"ACTIVE"
```

and

```Java
Constants.ACTIVE
```

when the real question should be:

> "How many times must the meaning of this string be maintained?"

---

## First principle: Duplication is not always bad

Many developers (and Sonar rules) implicitly assume:

```Java
if ("ACTIVE".equals(status))
```

appearing 5 times

↓

must become

```Java
Constants.ACTIVE
```

But there are actually **three kinds of duplication**:

### Bad duplication

```Java
"X-Correlation-Id"
```

appearing in 15 REST clients.

If the header changes:

```Java
"Correlation-Id"
```

you have 15 changes.

That's genuine maintenance debt.

---

### Acceptable duplication

```Java
logger.info("Customer not found");
```

appearing 3 times.

Changing one instance doesn't imply the others should change.

These are independent occurrences.

---

### Meaningful duplication

```Java
"ACTIVE"
```

in business rules.

The problem isn't the string.

The problem is that the business concept isn't modeled.

---

## The "Natural" Hierarchy I've Settled On

After years of fighting constants, I mentally classify:

### Level 0: Inline literals

```Java
if ("ACTIVE".equals(status))
```

Perfectly fine if used once or twice.

Readability is maximal.

---

### Level 1: Local constants

```Java
private static final String ACTIVE = "ACTIVE";
```

inside the class that owns the concept.

My favorite solution most of the time.

---

### Level 2: Domain vocabulary

```Java
CustomerStatusStrings.ACTIVE
```

when many classes share the same language.

---

### Level 3: Externalized data

properties:

```properties
status.active=ACTIVE
```

when values become configuration.

---

### Level 4: I18n

```properties
status.active=Active
status.inactive=Inactive
```

when values become user-facing text.

---

# The thing almost nobody talks about

Java doesn't really have a good answer here.

Look at this:

```Java
public static final String CUSTOMER_ID = "customerId";
```

Why must the identifier be different from the value?

It's duplication.

---

Compare with TypeScript:

```TypeScript
const Fields = {
    customerId: "customerId"
};
```

The structure feels more natural.

---

Or Python:

```Python
FIELDS = {
    "customerId": "customerId"
}
```

Even more natural.

---

Java forces you into:

```Java
CUSTOMER_ID
```

↓

```Java
customerId
```

which creates noise.

---

# What I'd love Java to have

Something like:

```Java
public interface CustomerFields {
    String customerId;
    String isActive;
    String createdDate;
}
```

where the compiler automatically assigns:

```Java
customerId -> "customerId"
isActive -> "isActive"
createdDate -> "createdDate"
```

Many modern languages have mechanisms close to this.

Java doesn't.

---

# If I were designing a large enterprise app today

I'd use something like:

```Java
public final class CustomerFields {

    private CustomerFields(){}

    public static final String CUSTOMER_ID = "customerId";
    public static final String IS_ACTIVE = "isActive";
    public static final String CREATED_DATE = "createdDate";
}
```

for contracts.

---

And:

```properties
customer.active=Active
customer.inactive=Inactive
```

for text.

---

And:

```Java
enum CustomerStatus {
    ACTIVE,
    INACTIVE
}
```

for business states.

---

And I'd allow:

```Java
if ("ACTIVE".equals(status))
```

when it's only local logic.

---

# My controversial opinion

Many Java teams extract **far too many constants**.

This:

```Java
private static final String SPACE = " ";
private static final String COLON = ":";
private static final String EMPTY = "";
private static final String COMMA = ",";
```

is often worse than:

```Java
":"
","
" "
""
```

because everybody already understands those literals.

The constant adds no knowledge.

---

# So, is there a better way?

I think the closest thing to a genuinely better solution is:

### ✅ Keep constants close to their domain

```Java
CustomerFields
ApiHeaders
DatabaseColumns
JsonProperties
```

### ✅ Externalize user text

```properties
messages.properties
```

### ✅ Use enums for states

```Java
ACTIVE
INACTIVE
```

### ✅ Allow simple literals when they're self-explanatory

```Java
" "
","
":"
```

### ❌ Avoid giant Constants.java

### ❌ Avoid turning every repeated string into a constant just to satisfy Sonar

---

If I had to summarize everything we've discussed into a single sentence:

> **The best practice is not "declare all strings as constants"; it's "give each string a home based on its purpose."**

That's the closest thing I've found to a solution that still feels natural after a codebase grows from 10 classes to 10,000 classes. 🤓
