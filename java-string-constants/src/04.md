Look, I know the enum with utility methods may be the most accptable solution for this.

```java
public class Strings {
    public final String active = "active";
    public final String ACTIVE = "ACTIVE";
    public final String Active = "Active";
    public final String is_active = "is active"; // I know, can collide with "is_active"
    public final String IS_ACTIVE = "IS ACTIVE";
    // and so on
}
```

---

Honestly? From a **language design perspective**, what you're proposing is actually quite reasonable.

The problem is that Java's identifier rules weren't designed for this use case.

When you write:

```Java
public class Strings {
    public final String active = "active";
    public final String ACTIVE = "ACTIVE";
    public final String Active = "Active";
}
```

you're essentially trying to create a **string dictionary** where:

- the field name mirrors the value
- auto-completion becomes the lookup mechanism
- the compiler provides type safety

That's not crazy at all.

The issue is that Java identifiers are **case-sensitive but otherwise limited**, so eventually you hit collisions:

```Java
is_active = "is active";
is_active = "is_active"; // impossible
```

and then the naming scheme falls apart.

---

## What's interesting is that many languages moved away from this pattern

For example, your `Strings` class is trying to act like:

```JSON
{
  "active": "active",
  "ACTIVE": "ACTIVE",
  "Active": "Active",
  "is active": "is active",
  "is_active": "is_active"
}
```

which is really a **dictionary/map**, not a class.

In a language with first-class module constants this feels natural.

In Java, not so much.

---

## The real objection I'd have is not the naming

It's the instantiation.

I'd never write:

```Java
public class Strings {
    public final String active = "active";
}
```

because every instance creates fields that are identical.

I'd at least make them static:

```Java
public final class Strings {
    private Strings() {}
    public static final String active = "active";
    public static final String ACTIVE = "ACTIVE";
    public static final String Active = "Active";
}
```

Even though the names break Java conventions.

---

## But here's where things get philosophical

Suppose I read:

```Java
if (status.equals(Strings.active))
```

What did I gain?

Compared to:

```Java
if (status.equals("active"))
```

Almost nothing.

In fact, I arguably lost readability because:

- `"active"` is immediately understandable
- `Strings.active` requires navigation

That's why many senior developers resist extracting simple literals.

---

## Where your idea becomes more compelling

When the strings stop being obvious.

Imagine:

```Java
public final class JsonFields {
    public static final String isActive = "is_active";
    public static final String accountReference = "account_reference_id";
    public static final String externalCorrelation = "external_correlation_identifier";
}
```

Now:

```Java
json.get(JsonFields.accountReference);
```

is better than:

```Java
json.get("account_reference_id");
```

because the Java identifier becomes documentation.

---

## The hidden problem you're discovering

You want:

```Java
Strings.active
Strings.ACTIVE
Strings.Active
Strings.is_active
Strings.isActive
Strings.IS_ACTIVE
```

because the **representation itself matters**.

That's usually a sign that the string isn't a business concept.

It's raw text.

And raw text tends to be best stored as data, not code.

Sometimes I see teams do this:

```java

public final class Vocabulary {

    public static final Map<String, String> WORDS =
        Map.ofEntries(
            entry("active", "active"),
            entry("ACTIVE", "ACTIVE"),
            entry("Active", "Active"),
            entry("is active", "is active"),
            entry("is_active", "is_active")
        );

}
```

or even:

```Java
public final class Vocabulary {
    public static final String ACTIVE_LOWER = "active";
    public static final String ACTIVE_UPPER = "ACTIVE";
    public static final String ACTIVE_TITLE = "Active";
}
```

which looks uglier, but avoids collisions.

---

## My take

I think Java is actually missing a construct here.

If I could invent one, I'd want something like:

```Java
strings {
    "active";
    "ACTIVE";
    "Active";
    "is active";
    "is_active";
}
```

with compile-time deduplication and IDE lookup.

That's closer to what you're trying to model.

Unfortunately Java only gives us:

- literals
- constants
- enums
- resource bundles
- maps

and none of them fit perfectly.

So if you're asking me as an architect rather than as a SonarQube follower:

> Is a dedicated class whose purpose is to centralize vocabulary strings inherently bad?

No.

Not at all.

I would actually prefer:

```Java
CustomerVocabulary.ACTIVE
CustomerVocabulary.IS_ACTIVE_COLUMN
CustomerVocabulary.IS_ACTIVE_LABEL
```

over a giant global `Constants` class.

What I would _not_ do is try to make the Java identifier mirror every possible text representation, because eventually the naming collisions become worse than the original duplication problem.

The moment you need:

```Java
"active"
"ACTIVE"
"Active"
"active "
" active"
"is active"
"is_active"
"is-active"
```

you're no longer modeling constants. You're modeling **text variants**, and Java field names are simply the wrong data structure for that job. That's where a vocabulary object, lookup table, or normalization layer starts to feel more natural than either constants or enums. 🤓
